文件传输与验收边界

MCP 上传采用一次性、短效 PUT URL：工具只签发地址和本地 curl 命令，本地客户端主动读取文件并上传；服务临时落盘后调用共享上传函数，返回资产标识才算完成。下载仍按大小选择内联字节或原 HTTP 流，资源链接明确 bytes_included=false。共享同一资产／任务标识，不把客户端路径当作服务端路径，不引入第二套文件服务。

当前只验证本包的示例结构、样例字节、配置和文档一致性，不证明HTTP/MCP协议或真实Task运行。M01–M12及模型验收均未运行。原evidence/revision-checks.json记录属于v1.3历史检查，本次结果单独存放。

1. 结论摘要

1.1 推荐方案

复用 agent-sandbox 的 /runner/submit、/runner/result、/runner/result_source、内存队列、Task/Runner 和进度钩子。拟增加 两个独立模型 Task（yue2_task、sheetsage2_task）、各自绑定的 Processor 与 environment，以及一个轻量服务型 Skill。翻唱、编辑以现有任务及文件交接组合，不各建一套模型执行器。需要乐谱审阅或修改的节点返回文件后释放任务执行资源，下一次以新阶段任务继续。S01S06

单台 AutoDL 上沿用现有 API + 本机 web_runner 子进程部署，不增加调度平台；在同一 API 侧增加 MCP 工具入口，复用四个 Runner 业务能力。runner_upload 只签发一次性、短效上传能力，实际字节由本地客户端 PUT 到同一监听器，再进入共享上传函数。模型进程分别使用 /root/yue-env/bin/python、拟议的 /root/sheetsage2-env/bin/python；权重与缓存位于 /root/checkpoint。原 Skill 的模型执行脚本保留在服务器端，Claude plugin Skill 只通过任务服务执行模型。S13

1.2 必要修改与限制

必要修改集中在：模型请求适配；environment 到子进程的实际传递；任务独立目录；真实错误/退出码解释；通用输入上传；现有结果接口的资源清单、鉴权和下载修正；音乐任务小型文件记录；请求去重与恢复；Claude plugin Skill 的调用入口映射。现有上传会删除用户评测目录，不能直接用作音乐输入。现有下载没有音乐清单白名单和相应主体校验，不能原样向公网开放。S05

以下项目不是已完成实测：AutoDL GPU、模型文件、两套 Python 环境、任务服务改造、插件封装后的真实任务调用与跨用户权限测试。用户工作区的 HEAD 和未提交修改也未取得；本次未执行仓库写入、分支切换、模型安装或业务代码修改；文档同步单独记录。

3.3 流水线组织

服务入口按独立模型分开：yue2_task 只绑定 yue2_processor，允许 generate|plan|all_modes|decode|score_check；sheetsage2_task 只绑定 sheetsage2_processor，仅允许 transcribe。每个 Processor 使用自己的 environment，不再以一个跨模型 Task 根据 operation 切换处理器。score_check 的 inspect/strip_chords/compare 在 YuE Processor 的轻量分支执行 abc_tools.py，不加载 GPU 模型，不增加第三个通用命令执行 Processor。

翻唱与编辑由 Skill 串联这些阶段。自动步骤在上一个任务已结束、资源校验通过后继续；需要用户选择或修改乐谱时，先结束当前服务任务，保留 workflow_id、source_task_id、产物引用；完成原步骤的检查和修改后再继续。等待期间不占 GPU，不要求新建一个长期挂起的父 Runner。无需服务端动态 DAG、任意脚本或可视化编排器。

4. 系统职责、交互流程与接口契约

4.1 职责与部署

Claude plugin Skill 沿原步骤组织请求、调用 runner_upload、在本地执行返回的 curl、确认资产响应、检查、修改和取得产物；API 负责认证、上传能力签发与消费、校验、任务身份、队列及资源访问；YuE2Task / SheetSage2Task 各自负责模型参数校验、固定 Processor 绑定和状态结果组织；Processor 负责环境解析、具体 CLI、进程与输出；文件层负责任务隔离与产物发布。

服务、Worker 与模型执行进程同在一台 AutoDL，共享本机任务目录；Claude plugin Skill 通过配置的 HTTPS 任务服务入口调用。源码自身没有证明公网 TLS/认证已经具备，入口配置和凭据注入是部署验收项。S05S13

4.2 现有与拟新增接口

接口 来源 本方案动作
POST /runner/upload 前版已规划的通用上传接口 通用文件上传；multipart 的 file、user_id；返回 asset_id、sha256、size_bytes。按认证用户隔离，不绑定模型或 operation
POST /runner/submit 已有 读取上传资产引用；校验所属用户、完整性与 Task 参数，使用现有队列
GET /runner/result?task_id=... 已有 查询真实任务状态和该任务已就绪的输出资源清单；每项包含 result_source_name
GET /runner/result_source?task_id=...&result_source_name=... 已有 取清单中指定资源，修正 MIME/文件名并校验归属；不新增输出下载路由
GET /runner/task-internal / POST /runner/task-update-internal 已有、内部 继续用于 Worker 拉取和进度更新；不作为 Skill 的公开接口

删除原设计的音乐专用上传和公开重发布接口，不替换为其他业务专用别名。输出写入和结果登记属于 Task/Processor 收尾；客户端下载失败只重新查询同一 task_id 并重取同一 result_source_name。两个 GET 均为读取，不以查询触发推理、搬运、重发布或业务状态变更。

MCP 的 runner_upload(file_path, client_os) 不把文件内容放入 JSON，也不让服务器读取客户端路径。它签发同一监听器的 PUT /api/uploads/{token}，返回本地可执行命令；PUT 路由使用 owner-only 临时文件，并调用与 POST /runner/upload 共用的上传函数。返回 asset_id、sha256、size_bytes 才表示资产可提交。该 PUT 路由是传输适配，不是新的 Runner 业务接口。

取消的最小范围是 Runner/执行器超时、进程取消信号的正确回收。本版不新增公开取消接口；停止当前等待不自动取消已经接受的服务任务。

现有 TaskRunnerResponse.code 是 JSON 字段，不自动改变 HTTP 状态。新的上传及模型任务校验错误使用真实 4xx/5xx；客户端检查 HTTP 和 JSON code 两者。保留既有 code/msg/data 外壳与旧任务调用方式。S05S15

4.3 提交示例及元数据

完整可解析示例位于 examples/。最小生成请求：

{
  "parameter": {"task_name": "yue2_task", "reset": false, "user_multi_task": false},
  "payload": {
    "code_input": {"userId": "user_demo", "workflow_id": "wf_demo"},
    "operation": "generate",
    "request": {
      "id": "rain_window",
      "style": "Mandarin piano pop, female voice, acoustic piano, 88 BPM",
      "lyrics": "[Verse]\n雨落在窗前\n[Chorus]\n把想念唱成诗篇",
      "cot": "full",
      "seed": 831001
    }

}

parameter/payload 与 code/msg/data 沿用现有外壳；yue2_task、sheetsage2_task、operation、workflow_id、request、asset/source引用均为拟新增业务契约。客户端 userId 只为兼容既有用户索引结构，API 根据认证主体核对并重写，不能据此授权。客户端不允许 _service、解释器、模型目录、脚本、GPU或输出路径。

拟新增头 Idempotency-Key 由客户端首次提交前生成并保存。Music API 在可信命名空间内按“认证主体+请求键”生成固定任务标识（例如 UUID5），并独占创建任务记录；该 ID 不承担访问控制。不同请求键允许同样音乐参数再次生成；同键不同规范化请求返回409；同键同请求返回原 task_id。规范化摘要涵盖task_name、operation、参数、资源内容摘要与必要关联信息，不因JSON空白变化重新采样。

API在接受请求时写入内部 payload._service={task_id, owner_id, request_digest, execution_profile_digest}；通过原 Dict 序列化传给 Worker。YuE2Task.prepare 和 SheetSage2Task.prepare 均为纯校验/转换，读取此 ID，不再生成随机 ID、读取用户输入路径或复制文件。这样 API 和 Worker 两次 prepare 使用同一标识，无需修改所有旧 Task 的 prepare 签名。S04S06

4.4 状态与执行结果

复用 info=pending、进度字符串、save_write、终态 end/error 与 finished。新音乐进度名称 dispatch_yue2_task / dispatch_sheetsage2_task 只是现有 str 状态机制中的值；对外真实阶段放在 result.stage：preparing/executing/validating/ready，不生成百分比。result 扩展 outcome、model_completed、delivery_status、artifacts、error；它们描述结果，不构成另一套调度状态机。S07

model_completed=true 只表示模型阶段完成并找到可验证输出；文件发布失败时可与 delivery_status=failed 并存。end + outcome=needs_review 表示文件可交付但截断或符号检查未通过，必须醒目提示，不将其等同音乐质量合格。

音乐 progress 上报完整结果快照，因为现有 post_task_update 会替换 result；两个模型 Task 复用音乐结果函数 save_music_result 按现有四路径内部约定组合清单，一次报告。不要把增强结果交给只发送四路径的基类保存方法后造成信息丢失。公共 serializer 从快照中剔除本地绝对路径与凭据，只输出资源键和相对下载地址。S05

6. 文件同步、产物交付和异常处理

6.1 通用输入上传、用户隔离与任务目录

唯一新增上传路径为 POST /runner/upload，采用 multipart/form-data：file 为单个文件，user_id 为资源所属用户。通用接口不接收 task_name、operation、environment 或客户端服务器路径；不调用模型、不安装依赖、不默认解压归档。文件大小和配额由通用上传配置控制，音频解码及 ABC 语法合法性由引用它的 Task/Processor 检查。

参考 extract_standard_file 的用户隔离思路，不复制其清空用户目录、解压评测 ZIP 的业务行为。请求中的 user_id 必须与认证主体对应；资源目录使用服务器规范化的用户标识，不直接拼接未经校验的字符串。S14

拟议布局：

/root/agent-sandbox-data/
  uploads/<canonical_user_id>/<asset_id>/
    source.<ext>             服务端命名；原始文件名保存在记录中
    asset.json               user_id、asset_id、sha256、size_bytes、相对路径
  tasks/<service_task_id>/
    task.json                API维护请求、主体、真实状态与已绑定输入
    input/                   原始/执行请求及任务使用的输入文件
    work/native/             由上游helper创建的新输出目录
    artifacts/               已校验完成的文件
    logs/stdout.log
    logs/stderr.log
    result-manifest.json     内部输出清单及完成记录

每次上传分配一个新的 asset_id，不覆盖同名文件、不删除该用户其他上传。写入临时位置时计算实际 sha256 和 size_bytes，完成写入并原子登记后才返回成功；中断上传不产生可引用资产。模型权重不参与此接口的普通任务输入同步。

返回 code/msg/data 外壳，data 中含 asset_id、sha256、size_bytes。提交阶段引用 asset_id：转录使用 payload.audio_asset_id；用户修改后的 ABC 使用 payload.abc_source.asset_id。sha256/size_bytes 供调用方核对，服务器始终以资产登记及实际文件校验为准，不把客户端回传的摘要当作授权或完整性证明。无需为传回摘要再增加重复的模型参数。

/runner/submit 接受前检查资产已完成、归属匹配、记录存在、大小与摘要一致，并将输入引用绑定到该服务任务；Task.prepare 保持纯转换，不在 API/Worker 两次 prepare 中重复复制文件。dispatch 准备阶段再通过共用资源解析函数取得受控路径，按需将小型输入复制到任务 input/；已绑定运行任务的输入不能被清理。任一输入失败在启动模型前报告。

已有输出作为后续任务输入时使用 {task_id, result_source_name}，服务内部按同一用户权限解析，无需下载再上传；按原步骤修改过的文件作为新输入上传。普通文本 request 可以直接进入 submit JSON，无需额外上传一次。绝对路径、..、NUL、符号链接逃逸及跨用户引用均拒绝。

6.2 产物清单与原生结果

普通生成原生audio.flac及request/config/result、plan/tokens/latent保留在服务器；外发默认音频、请求、结果摘要、存在时的ABC。latent/token不是任务状态内嵌数据，也不随每次下载自动发送。转录只列实际存在的score.abc、MIDI及报告，不把某个可选文件名写死成必有。S21

先执行原生verify_result或转录manifest/ABC检查，再检查helper的run.json、abc_check、退出码。然后由轻量清单记录result_source_name、相对路径、bytes、SHA256、MIME、音频属性、请求摘要、模型和代码版本、解释器。发布是同文件系统原子rename或资源层已有提交操作；API仅暴露ready记录，不提供还在写入的文件。S19S22

完整结果目录和可交付清单不应重复复制所有latent。优先将已核验目录原子移到artifacts/native，再对其中文件登记与 result_source_name 对应的路径；移动后内部相对manifest仍可验证。若原生输出包含绝对路径元数据，只作为来源记录不再用于资源寻址。请求和随机种子随任务归档，密钥不入档。

输出寻址约定

GET /runner/result 的 data.result.artifacts 为拟扩展的清单字段；每个已就绪条目包含 result_source_name、filename、media_type、size_bytes、sha256。清单项必须逐一对应内部 result[result_source_name] 的已登记文件路径，以兼容现有 result_source 寻址方式。内部路径继续存在，公共 JSON 不返回服务器绝对路径；旧任务的 result_path、log_run_path 等已有键仍可沿用，不强制改名。

客户端只从实际清单选取名称，用既有查询参数 task_id + result_source_name 获取文件。无需额外 artifact_id、输出 asset_id、资源清单端点或下载URL分配端点。可选文件未产生就不列出，metadata 字段不能被当作文件名访问。读取端按清单白名单与所属用户检查；未就绪、缺失、过期或无权限分别返回错误，禁止把 JSON 错误体保存成音频。大小及摘要是示例元数据时必须标注，真实响应只能填真实值。

6.3 必须正确解释退出码

执行类型 判断
generate exit0且run.results.complete、原生校验通过→正常交付
generate/plan exit1可能是needs_review，不一定模型异常；按truncated与abc_check解释，交付时加警告并阻断自动进入要求乐谱合格的下一阶段
all_modes 每个模式单独记录；部分失败→outcome=partial、info=error，保留成功文件，不声称全部成功
decode 验证source完整原生结果和主模型identity；退出1可能继承截断标记，不能称断点恢复
transcribe 缺ABC或abc_error即失败；已有LAB/MIDI不等于翻唱前置成功
score_check compare exit1表示不满足所检查的不变量；它是检查结果，不等于工具崩溃；有意修改节奏时记录允许差异，不伪造旋律未变
exit2 / 进程异常 解析失败、环境错误或执行异常，依据stderr/failure.json分类

这些分支直接来自辅助脚本，单独读取result.json里的complete会漏掉需复核情况。S19S27

6.4 文件完成、读取重试与恢复

Task/Processor 负责完成文件写入、原生校验和结果登记；这些步骤成功后，已就绪清单随原进度机制写入任务结果，调用方通过现有两个 GET 读取。delivery_status=ready 表示文件和寻址记录已就绪，不表示客户端已经下载成功；无需客户端确认下载接口。

模型已完成而文件落盘/登记失败：保留已有原生结果及诊断，记录 model_completed=true, delivery_status=failed，按既有 error 结束。可在服务端原有收尾/维护流程中有限重试登记；未恢复时向用户明确报告。不提供公开重发布接口，也不把恢复操作藏进 GET。 真正丢失或损坏的音频无法靠再次读取恢复，修复前不能列为可下载；重新采样需要新的明确请求。

客户端下载失败：重新 GET /runner/result 读取同一任务的现有清单，再按同一个 result_source_name GET /runner/result_source；已确认名称和摘要未变时可以直接重试后者。下载先写 .part，校验后再 rename，最多3次（客户端策略值）。读取失败不得重新 POST /runner/submit，也不得改变 seed、歌词或采样参数。无权限不自动重试，临时网络错误才进入有限重试。

现有任务只在内存保留并按TTL删除。为防止音频尚在磁盘而查询不可恢复，拟增音乐任务专用小型文件记录，复用现有维护循环，不引入数据库/队列平台。API是task.json唯一写入者；Worker写结果manifest，进度经现有内部接口更新。API收到终态丢失时可从已完成manifest校正，不凭音频文件存在猜成功。API重启后已排队音乐任务可按既有队列重建；曾经执行中的任务标记interrupted，检查结果/子进程后人工决定，不自动重新采样。S11

task创建与Idempotency-Key占位要使用独占创建及原子JSON写入；记录完整落盘后再入队/返回成功。重复看到初始化中的目录返回可重试的409，不另分配采样任务；崩溃遗留空记录在启动检查中处理。此处只解决当前任务交付与去重，不宣称exactly-once推理或模型续跑。

清理按样例7日保留期（可配置）处理已结束任务及无人引用的输入，保留故障诊断宽限期；不删运行中、发布中和下载持有句柄的对象。与清理竞争时用临时占用标记/受控文件句柄，并通过测试确认。需长期保留的音频下载并保存，不把会过期的服务资源地址当作永久文件。

6.5 权限边界

当前公共runner路由没有这里需要的用户认证；内部nonce仅用于Worker。音乐部署的外部submit必须在入口强制task_name属于{yue2_task, sheetsage2_task}白名单，并校验各自operation，不能通过改成ResearchAgent或旧评测task绕过音乐认证与执行限制。拟在音乐部署配置一份服务端管理的“令牌摘要→用户主体”映射，0600权限，调用凭据由服务配置安全提供，并与对应用户绑定，不放在提示词、请求产物或argv。单用户试用可只有一条映射；多用户必须逐用户分配，不能所有用户共享无归属的key。部署后的密钥发放/轮换属于待验收配置，不声称已连接秘密管理系统。S05

通用 upload、submit、result、result_source 均核对同一主体；上传路由不依赖两个音乐 Task 的枚举，具体任务的业务入口继续各自验证。code_input.userId只能与主体一致。内部nonce端点禁止公网直接访问，管理日志和旧评测接口不对不可信音乐客户端开放；生产入口认证默认开启。旧非音乐部署若保持兼容，仍须明确其原有安全限制，不能凭项目名称“sandbox”认定为安全执行隔离。

6.6 生命周期、超时与GPU并发

stderr/stdout并行消费、限长摘要、完整受控日志、退出码入结果。超时用总deadline，不继承旧60秒静默终止。子进程单独会话/进程组，取消或超时先TERM，宽限期后KILL，await回收，确认后才报告finished释放任务槽。测试还需检查上游有无脱离进程组的后代。S09

本期AutoDL使用一个API实例、一个受管Worker、max_ongoing_tasks=1；控制点是唯一API维护的ongoing队列，而非某个Processor局部锁。Worker现有semaphore100不等于GPU并发100；本配置从取任务入口限制到1。代价是该实例CPU任务也顺序执行，先接受这一明确代价，不建立资源调度器。S05S11

此限制不覆盖其他API实例或用户手工启动的GPU进程；部署验收禁止同GPU另开绕过入口的执行服务。Worker意外死亡时，音乐模式不要沿旧逻辑立即重新派任务：当前任务标记错误、停止取新任务，清理残存模型进程并确认资源释放后恢复服务。SIGKILL场景不能靠Python finally承诺全部清理；本期采用失败后暂停调度与运维恢复，不承诺无人值守自愈。S13

web_client_timeout原实现依据requested_at清除尚未开始的任务，result查询并不刷新该字段。音乐部署设为-1，接受的任务不因调用连接断开消失；容量和排队超时若要增加，应使用显式队列策略，而非借用“客户端断开”语义。S05

5. 保持原业务步骤

5.1 生成并保留乐谱

从原模板整理 style、lyrics、cot、seed 及已确认支持的其他字段。按需求选择 full、melody 或 off，提交相应生成任务。full/melody 和 off 的产物差异沿用上游语义，off 不虚构可编辑 ABC。S17

取得任务标识后查询状态；完成后读取音频、请求、结果元数据和实际存在的乐谱。按原步骤检查截断、符号检查和音乐结果，保留模型／解码器身份。比较多个模式时保留每个模式的结果与失败，不把部分成功说成全部成功。

5.2 转录与录音翻唱

上传原音频 → 提交转录任务 → 取得 ABC、转录警告及实际产物 → 检查并按需修正漏音、拍号或调性 → 按原要求去除和弦条件并检查保留声部 → 用已检查的 ABC、目标风格和歌词提交 cot=melody 生成 → 取得新音频并试听比较。

需要修订时保留原音频和原始转录；新 ABC 上传为新资产。strip_chords 产生新谱后，后续生成必须引用该步骤输出的资源名，不能误用处理前乐谱。转录失败或 ABC 不可用时停止后续采样。保留和声时按原工作流采用完整转录与 cot=full，不把它称为仅旋律条件翻唱。S17

5.3 编辑与再生成

取得原完整计划和基线音频并保留原稿 → 明确允许修改及必须保留的音高、节奏、声部、速度等约束 → 另写 ABC、歌词或风格修改稿 → 上传新谱 → 按原步骤运行 inspect/compare → 检查通过或明确记录有意变化后提交修改稿条件生成 → 比较修改前后音频与乐谱。

检查以音乐事件而非字符相等为依据。修改后的乐谱必须真实进入后续生成输入；不能省略 ABC 后生成一份新计划。旧 latent 重解码不等于改词或音乐编辑。上游没有的局部音频修补、声纹保留、音素强制对齐等能力不增加承诺。S17

5.4 取得可听结果与对比材料

先读任务结果清单，再逐项下载需要的音频、请求、修改前后 ABC、检查报告及实际生成的评估资料。继续原试听比较步骤；需要比较页时复用原辅助方式，不增加新的应用界面或媒体服务。可播放不等于音乐质量合格，符号检查通过不等于声学结果严格实现了所有约束。S17

6. 异步调用只增加任务等待，不改变业务步骤

首次提交前保存请求键；接受后保存 task_name、task_id、输入引用和当前步骤。多阶段流程可沿用 workflow_id 记录关联；不另建会话或调度模型。

每次等待有上限：建议每5秒查询，最多12次且总等待不超过60秒，任一条件先到即结束本次等待，终态立即退出。这些是调用策略，不是模型长度限制。等待结束后返回真实任务标识和阶段；再次查询同一任务，不重新提交采样。

result_source_name 只能使用真实清单中的值；下载失败最多3次重取同一资源。文件大小与校验和通过后再完成本地保存。认证失败、文件缺失或登记失败明确报告；两个 GET 不触发修复、发布或模型重跑。服务没有提供的自动通知、百分比进度和断点续跑不作承诺。

Notion 独立页：https://app.notion.com/p/3de30b7547c381d98aa4d196c5b52503

1. 接口边界

新增仅 POST /runner/upload。继续使用 POST /runner/submit、GET /runner/result、GET /runner/result_source；删除 /runner/music-inputs 和 /runner/music-publish-retry 两个原拟议接口，不保留别名。

通用上传不属于YuE或SheetSage2业务；按user_id隔离资产，任务运行仍各自绑定preprocess和environment。输出是任务已有结果，不需要额外“发布”API。

2. 上传与提交

multipart字段为file、user_id。服务端以认证主体核对user_id，将文件存到uploads/<canonical_user_id>/<asset_id>/，计算SHA256和实际大小，全部写入完成后原子登记并返回asset_id、sha256、size_bytes。

同用户同文件名连续上传也得到独立asset_id，不覆盖、不删除已有文件；不沿用extract_standard_file的清目录和ZIP解压行为。路径、大小、配额与归属是通用层约束；音频/ABC是否符合模型输入由相应Task/Processor验证。

已有报文最小改动：转录以payload.audio_asset_id引用上传结果；改谱生成以payload.abc_source.asset_id引用新ABC。sha256/size_bytes供完整性核对，不必重复作为模型参数提交；服务端以自己的登记和实际文件为准。Task接受前检查资源可用且归属一致，dispatch准备阶段解析受控路径，再传给对应preprocess执行。

3. 结果清单与文件读取

GET /runner/result?task_id=…返回原code/msg/data外壳、真实状态及拟扩展的data.result.artifacts列表。列表每项提供result_source_name、filename、media_type、size_bytes、sha256。资源名对应服务器已登记的result同名路径键；公共响应隐藏绝对路径，不改变旧任务的result_path/log_run_path等资源键。

客户端下载：GET /runner/result_source?task_id=…&result_source_name=…。名称取自真实清单，不从客户端文件名拼服务器路径，不另发明artifact_id。任务输出传给后续Task时沿用{task_id,result_source_name}，同用户权限检查后可在服务端直接读取，无需上传副本。

4. 完成与重试

文件写入、校验和登记属于Task/Processor收尾。只有完整文件进入清单；GET是只读接口，不触发发布、重新采样或登记修复。下载失败可重新取得清单并重试同一资源，保留task_id、名称和原始摘要，先写.part并验证，再完成本地保存。

模型完成但登记失败时保留原生结果，报告既有error与必要结果字段；原收尾/维护流程可在服务端有限恢复，未恢复不虚构可下载文件。不增加公开重发布接口。真实文件损坏或丢失无法靠GET修复，重新生成须明确创建新任务。

Runner 接口 MCP 封装与文件传输

版本：1.6｜日期：2026-09-18｜修正远程上传边界；未实现或部署 MCP endpoint。

1. 目标与边界

将 agent-sandbox 的四个 Runner 接口作为四个 MCP 工具对外暴露。MCP 是任务服务的另一种调用入口，位于 API 一侧，不是模型执行后端。v1.4 的外部执行链设计撤回，本版取代其 MCP 文档、配置、示例和第四张时序图。

Claude plugin Skill
    → agent-sandbox /mcp
    → 四个 Runner 工具
    → 同一套 Runner 业务函数
    → 原有队列、Task、preprocess、模型环境与文件记录

已有 HTTP 调用 → 原 /runner/* 路由 → 同一套 Runner 业务函数

不因 MCP 新增 Task、Processor、模型环境、后端 job ID、文件桥接服务或第二个队列。MCP 只封装 agent-sandbox 已有 Runner 能力，不引入其他运行服务。

原模型绑定保持：

yue2_task       → yue2_processor       → /root/yue-env/bin/python
sheetsage2_task → sheetsage2_processor → /root/sheetsage2-env/bin/python

这里的模型任务是前版已确定的待实施适配；本次没有将其标记为已上线。

2. 四个接口一一映射

工具名为本版拟议名称，均通过同一个 /mcp endpoint 的 tools/call 调用；不是再增加四条 HTTP 路由。

既有／已规划 HTTP 能力 MCP 工具 MCP 参数与返回
POST /runner/upload（前版已规划） runner_upload file_path、client_os；返回一次性、短效 PUT URL 与本地 curl 命令；PUT 成功后返回 asset_id/sha256/size_bytes
POST /runner/submit runner_submit 保留原 parameter、payload；可选 idempotency_key 对应 HTTP 的请求键；返回相同 task_id 和接受状态
GET /runner/result runner_result task_id；返回同一任务状态及 data.result.artifacts 资源清单
GET /runner/result_source runner_result_source task_id、result_source_name；新增仅用于传输选择的 mode=auto/inline/link；返回原文件字节的编码或原下载入口的资源链接

parameter/payload、上传 asset_id、服务 task_id、清单 result_source_name 都不另起一套命名空间。MCP JSON-RPC id 只关联一次协议调用，不作为任务 ID、请求去重键或用户身份。协议工具发现、调用和结果结构依据官方 Tools 规范；上述工具名和参数是本项目设计，不是 MCP 内置方法。MCP01

3. 共用业务实现，不复制调度逻辑

将路由中需要复用的业务动作提取为内部函数，或直接复用已有等价函数。拟议名称为 upload_input、submit_task、get_task_result、open_task_resource；名称不代表源码中已经存在。

HTTP 路由和 MCP 工具均传入认证主体，调用同一业务函数。HTTP 层处理 multipart、查询参数、HTTP 状态和 FileResponse；MCP 层处理 JSON 参数、文件编码、工具结果及 isError。业务函数仍负责用户隔离、路径约束、参数校验、请求键、入队、状态和文件寻址。

下载业务函数返回经过授权的文件句柄／文件描述和元数据，由两种协议分别输出；不要把 FastAPI 的 FileResponse 对象直接塞进 MCP JSON。上传同样接受流或受控临时文件，不能把 JSON 字符串假装成跨机器可访问的路径。

适配器不得自行再运行一次 prepare、创建第二个任务标识、重新入队，或直接调用模型脚本。MCP 工具错误不能绕过原 HTTP 路由的认证及 Task 白名单。工具发现只列当前部署实际允许的工具，任务授权继续由原提交逻辑处理。

4. 上传适配：云端签发，本地客户端主动上传

4.1 agent-sandbox 目标流程

runner_upload(file_path, client_os) 不在 MCP 消息中传 Base64，也不让远程服务器读取调用方路径。工具只校验路径元数据，随后在 agent-sandbox 的 MCP HTTP 服务签发一次性、短效 PUT URL，并返回已经引用本地路径的 curl 或 curl.exe 命令。

Claude plugin Skill → runner_upload(file_path, client_os)
agent-sandbox /mcp → 返回一次性、短效 PUT URL 与 curl 命令
本地 AI 客户端 → 执行 curl，读取本机文件并 PUT
/api/uploads/{token} → owner-only 临时文件 → Runner 共用 upload_input
Runner 资产库 → 返回 asset_id、sha256、size_bytes
Claude plugin Skill → 将 asset_id 写入 runner_submit

URL 采用五分钟有效期和单次使用语义；具体文件上限沿用 Runner 上传配置。token 本身就是上传授权，PUT 不附加 Authorization。服务先消费 token，再有界流式写入 owner-only 临时文件，并在所有退出路径清理临时目录。只有共用上传函数完成用户隔离、摘要计算和资产登记后，才返回资产信息。

4.2 Runner 对应适配

runner_upload(file_path, client_os) 的完整控制流如下：

Claude plugin Skill → runner_upload(file_path, client_os)
agent-sandbox /mcp → 签发 /api/uploads/{token} 与 curl/curl.exe 命令
Skill 所在本地客户端 → 执行命令并直接读取本机文件
/api/uploads/{token} → 消费 token → owner-only 临时文件 → upload_input
Runner 资产库 → 按认证主体隔离并登记
PUT 响应 → asset_id、sha256、size_bytes
Claude plugin Skill → 将 asset_id 放入 runner_submit

file_path 只用于生成客户端命令和取得安全文件名；远程服务不打开该路径。/api/uploads/{token} 是同一 HTTP 应用的传输适配路由，不是第五个 Runner 业务接口。原 POST /runner/upload 继续供直接 HTTP 客户端使用，并与 PUT 路由共用上传函数、权限检查和资产登记。

只取得命令不算完成，临时落盘也不算完成；PUT 返回 asset_id、sha256、size_bytes 后资产才可提交。URL 已使用、过期、篡改、超限或传输失败时，重新调用 runner_upload；不能重跑旧命令、补 Authorization 或直接提交。反向代理必须同时转发 /mcp 与 /api/uploads/，并提供可信的完整公开 origin。

5. 下载适配：同一任务同一资源

先调用 runner_result(task_id) 取得资源清单，选择清单中的 result_source_name，再调用 runner_result_source。工具读取前仍检查用户归属、资源名称白名单、文件是否完整且可读取。不能以 task_id 可猜测、MCP 已连接或 URI 存在作为授权依据。

mode 行为 字节交付状态
auto（默认） 小于或等于内联上限返回 Base64；更大文件返回 resource_link 结果中的 delivery 明确为 inline 或 link
inline 对同一文件作有界读取，返回无损 Base64 与原文件元数据；超限报错 bytes_included=true，不代表调用侧已保存到本地
link 返回指向原 GET /runner/result_source?task_id=...&result_source_name=... 的 HTTPS 资源链接及元数据 bytes_included=false，不能报告“下载完成”

内联结果放入 MCP structuredContent，字段包含 code/msg/data，data 内含 delivery/encoding/content_base64 和文件名、媒体类型、字节数、SHA256；为兼容仅显示文本结果的客户端，同步提供序列化 JSON 文本。该方式是本项目的工具数据契约，不是把任意文件误标成图片或音频内容块。

链接结果使用标准 resource_link 加结构化元数据，不创建额外 /files 路由或通用 resources/read 平台。链接由配置的公共服务基址与受控 query 参数构造，不信任入站 Host 头或调用方 URL。链接不携带长期凭据；调用侧访问原下载接口时使用该接口接受的认证凭据。不能假设每个 MCP 客户端会自动替资源链接带认证，缺少能力时明确显示“需要授权下载”。MCP01

完整音乐优先使用链接与原 HTTP 文件流。HTTP 下载保持正确媒体类型及文件名；调用侧写临时文件，核对实际大小与 SHA256 后完成本地保存。Base64 内联同样校验解码后的原始字节，不经过有损格式转换。元数据来自实际产物记录，不使用示例摘要冒充验证结果。

重复下载只读取同一文件；不调用 submit，不重新采样，不做隐式发布或修复。缺失、损坏、过期、无权限分别返回明确错误。Range、断点传输和自动持久下载均不在未验证时宣称支持。

6. 任务状态、错误与权限

runner_submit 接受后立即返回原 task_id；原 Runner 继续执行。runner_result 每次只查询一次，Skill 沿原有限等待规则组织查询，MCP 适配器不另建任务轮询队列。断开 MCP 或停止等待不等于取消服务端已接受的任务。

HTTP 与 MCP 对同一主体、同一请求键、同一规范化参数必须得到同一任务。MCP 的 idempotency_key 进入同一去重函数，不能把 JSON-RPC id 当键。请求键存在于前版设计，仍需业务实现与并发测试后才能承诺生效；禁止遇到协议错误自动改用 HTTP 再提交一次。

业务操作拒绝返回 isError=true 和原错误类别；鉴权失败在传输入口执行。合法状态查询即使读到任务 info=error，查询本身仍成功：isError=false，保留任务失败状态，不混淆协议失败与模型失败。非法工具名或协议参数按 SDK 协议错误处理。

下载链接模式也必须先授权。身份从每次请求的认证上下文取得，不从工具参数自证；工具 user_id 或 payload 中旧用户字段必须核对。同一主体跨 HTTP/MCP 能读取同一资产与任务，不同主体都被拒绝。只读工具的 annotations 仅用于描述，不代替权限控制。MCP01

7. MCP endpoint 与配置

推荐把官方 SDK 提供的 MCP HTTP 应用挂载到 agent-sandbox 现有 ASGI 应用的 /mcp，共用服务生命周期和业务函数。保持原 HTTP 路由；MCP 关闭时原任务服务仍可启动。正确组合子应用 lifespan 与路径前缀，避免重复变成 /mcp/mcp。这是部署设计，未实际完成挂载。

采用 Streamable HTTP；本版将 2025-11-25 作为一个明确的互操作测试基线，不声称它是当前最新版本或所有版本均兼容。具体协议协商、GET/SSE、会话及关闭行为由锁定 SDK 对应版本实现，不从不同版本拼装规则。上线前执行 TLS、Origin/Host、认证、请求大小、超时及资源权限测试。MCP02

现有依赖与 MCP SDK 的兼容性需要先在独立测试环境求解和回归；不能未经验证升级主服务，也不因为 MCP 新建一个模型环境。优先同应用挂载，若依赖检查不通过，明确保留部署阻塞而非默默引入另一执行架构。
